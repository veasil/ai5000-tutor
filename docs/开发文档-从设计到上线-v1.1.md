## 2. 技术框架（v1.1 轻量化）

### 2.1 架构总览
```
[孩子端]──┐
[家长端]──┼─▶ Next.js 15 App Router（一个工程搞定前后端）
[运营页]──┘        │
                   ├─▶ content/*.json  ── 所有文案/关卡/卡牌/prompt（不入代码）
                   ├─▶ lib/ai/client.ts ─▶ Anthropic SDK（流式，服务端中转，密钥不入前端）
                   └─▶ 轻量 DB（Turso/SQLite 或 Neon free）── 仅存 journey 状态
```

### 2.2 砍掉与保留
| 关注点 | v1.0 重型 | v1.1 轻量 | 理由 |
|--------|-----------|-----------|------|
| 文本内容 | 硬编码 / DB | **`content/*.json`（强制）** | 文本居多，改文案不动代码 |
| 用户状态 | PostgreSQL + Prisma | **Turso/SQLite**，1 张 `journey` 表（state 存 JSON blob） | 每用户状态极小 |
| 作品/代码库 | 多表 | journey 内 JSON 字段 | 无需关系建模 |
| 对话缓存 | Redis | **删除** | 短对话直接读 DB |
| 审核队列 | BullMQ | **删除** | MVP 同步审核 / 人工后台 |
| AI 调用 | `lib/ai/` 封装 | **保留不变** | 密钥安全红线 |
| 监控 | Sentry | MVP 可后置 / 用 Vercel 内建日志 | 减负 |

> **唯一不能省**：AI 流式必须服务端中转，`ANTHROPIC_API_KEY` 绝不进前端/仓库。

### 2.3 内容配置化目录（v1.1 核心新增）
```
content/
├── levels/level-{1..10}.json   # 每关：任务说明 / 提问顺序 / 输出字段 schema / 文案，引用模板id
├── cards/                       # 风险情景卡（运营要改）
├── ui/                          # 界面文案 key→text（按钮/提示/空状态）
└── prompts/                     # 小伍 system / stage / guardrails（也别硬编码）
```
孩子端渲染读 `content/ui/*`；`level-configs` 只存结构，文案引 key。**改卡牌/文案 = 改 JSON。**

### 2.4 保留的关键约定（来自 `CLAUDE.md`，不变）
1. AI 调用全走 `lib/ai/client.ts`（token 计数/限流/重试/流式）。
2. Prompt 分层：`system → stages/level-N → guardrails →` 最近 20 条对话。
3. 结构化输出：每轮返回 `text` + `structuredOutput`(JSON)，后者写 journey 字段（字段见 `state-machine.ts` `LevelOutput`）。
4. 红灯：`safety.ts` 对输入/输出双向检查；触发即中断、写 `safetyFlags`、返回安全文案；自伤/威胁直接跳出显示求助资源。
5. 不可跳关：`canAdvanceToLevel` 校验前置；第 9 关过了才能 `draft→reviewing`。
6. 匿名 ID `小伍创客[4位数字]`，不收集真实身份。
7. Server Action 统一返回 `{ok:true,data} | {ok:false,error,code?}`。
8. 时间戳用 `DateTime`，禁毫秒。

### 2.5 设计 → 代码
- `styles.css :root` 令牌 → Tailwind v4 `@theme`；shadcn 二次封装 `Bubble`/`Card`/`LevelTile`/`GuideBand`/`StateView`。
- 5 个静态屏 = 像素级验收基线。

按 `state-machine.ts` 的 `LevelOutput` 把 10 关聚成 **3+1 套模板**：

| 模板 | 适用关卡 | 交互形态 | 输出字段示例 |
|------|----------|----------|--------------|

## 7. 附：Pencil 设计的目的与关卡设计顺序

### 7.1 为什么需要现在这几个屏
Pencil 设计稿在本项目承担三个作用，**不是为了"把每个页面都画出来"**：
1. **设计令牌的来源**：颜色/字体/间距/描边/投影从画稿沉淀进 `styles.css :root` → 再进 Tailwind theme。
2. **开发验收基线**：每个"布局原型"是一类页面的像素级参照，开发照着还原。
3. **信息架构验证**：在写代码前，用画稿确认"孩子怎么一步步被引导"是否成立。

所以现在 5 屏各代表**一类布局原型**（Hub / Gallery / Progression / System-State / 关卡模板），覆盖了全站布局种类，而不是 5 个具体页面。

### 7.2 10 关：画模板，不画 40 个屏
**画模板/结构，让关卡调用模板填内容。** 10 关若每关画全屏 = 重复劳动且无法配置化；正确做法是画出 §3 的 3+1 套模板，关卡只在 `content/levels/level-N.json` 里填"提问顺序 + 输出字段 + 文案"，运行时套模板渲染。

### 7.3 先结构还是先模板？——先定关卡结构，再抽模板（务实顺序）
不是纯自顶向下，也不是纯自底向上，按这个序最省：
1. **先定义每关"做什么"**（交互意图 + 输出字段）——这一步已基本完成，写在 `state-machine.ts` 的 `LevelOutput` 里。
2. **聚类**：把 10 关按交互形态归类 → 自然落成 A/B/C/D（7+1+1+1）。
3. **每类挑 1 关画到高保真**（`level4` 就是模板 A 的"发现稿"）——通过画一关具体的，发现这一类的通用结构。
4. **抽象成模板**：去掉具体文案，留下槽位（标题槽/提问气泡槽/输入区/结构化输出卡/推进按钮）。
5. **其余同类关卡 = 填 JSON 进模板**，不再画。

> 一句话：**结构先于模板，但模板要靠"画透一关"才能抽出来。** 你已经有 `LevelOutput`（结构）和 `level4`（模板 A 发现稿），下一步就是画模板 B（Demo 生成）和 D（发布），C（检查清单）可直接用 shadcn 列表件。
